## 做了什么

### 关键概念

**① 余额（`junction_flush`）定稿**——0.15 不是钟，是记账本：

```
余额 = 0.15 − 本波内第 2 条起新入队 move 的 min_move_t 之和
```

- `min_move_t = move_d / velocity` 在 `Move.__init__`（`toolhead.py:41`）
  **构造时**就算好——扣款虽然写在 `calc_junction` 后一行（`:191`），但
  **扣的时间和拐角计算没有数据依赖**，只是排版相邻；
- 首条 move 两样都跳过（`len==1` 直接 return，没有前驱算不了拐角）；
- 扣穿（≤0）在入队瞬间同步触发 lazy flush——**事件，非轮询**；
- 每次规划完无条件重置 0.15（`:136`），**留在队列里的尾巴不计入新账本**；
- 扣穿可以越过 0（如 0.13 → −0.87），因为扣款只在 move 到来的瞬间发生，
  两次入队之间隔多久墙钟都不动余额。

| 它不是 | 它是 |
| -- | -- |
| 距上次规划的时间 | 纯按 move 时长累减的倒计时 |
| 队列条数/字节数 | 100 条 0.5 mm 短 move 只扣 0.02 s |
| 剩余缓冲水位 | 只活在 toolhead 内部，serialqueue 不知道它 |

**② req_clock 与 flush_clock 定稿**：

- **`flush_clock`** = `flush_time` 过桥换算（`clock_from_time`），
  **全局一个**，是本波的两条截止线：
  ① 压缩截止（`steppersync.c:89`，只压首脉冲 ≤ 它的批次）；
  ② 槽位闸截止（`:320`，批次起点 > 它 → 整批滞留）。
  一句话：**这一波干到哪个时刻为止**。
- **`req_clock`** = 每条消息自带的"期望出门时刻"，**每条一个**，三个来源：

| 来源 | 值 | 语义 |
| -- | -- | -- |
| step 批（C 侧） | `last_step_clock` = 上一批末脉冲（`stepcompress.c:359`） | 本批起点 |
| 普通命令（Python 侧） | 调用方传入，默认 0 | 期望送达时刻（endstop 查询等） |
| 后台优先级消息 | `BACKGROUND_PRIORITY_CLOCK` 哨兵（`serialqueue.h:9`） | 贴着发送节拍走 |

  三个消费点：排序（`:485` req_clock 小者先拼帧）、发送节拍
  （`:645-659` 睡醒计算）、后台哨兵改写（`:634-641`，改写为
  "端口空闲 + 0.105 s"）。

**③ min_clock 定稿**——补充 11-17 概念④（一生链与记忆锚点在那边）之外的结论：

- 字段层面 `struct queue_message` 两个都有，任何消息都带，值可为 0；
- **三类来源**：普通命令=调用方显式传（常 0，homing 场景传当前时钟防插队）；
  step 批=影子堆记账（出生=上一批末脉冲，出门=堆顶，见 11-17④）；
  后台消息=哨兵。

**④ 影子堆堆顶 `next_avail`**（固件"加载即释放"的事实与容量握手见 11-17⑤）。
本篇新增两样：早先错误认知的修正记录 + 堆顶的读法：

| 早先说法 | 源码事实 |
| -- | -- |
| 槽位释放时刻 = 批次**末**脉冲 | = 批次**起点**（加载即释放） |
| 堆顶 = 最早结束的批次末尾 | = 最早**开始执行**的排队 move 的起点 |
| 执行中的 move 占槽位 | 不占（在 `struct stepper` 里） |

堆顶逐行（`steppersync.c:323-330`）：
① 读堆顶（所有已占用槽位最早释放的时刻）→ ② `heap_replace` 用本批起点
换掉旧堆顶（时间单调，堆自动前移）→ ③ 旧堆顶塞进报文 = 到货许可证。

**停车场模型**：每入场一辆车登记离场时间；新车能不能进看**最早离场的车位**；
车流稳定时那永远属于入口处最早进来那辆——**到货即换坑，MCU 队列永不过载**。

两种水位对回实测：稳态 → 堆顶 ≈ now → `min_clock ≈ now` → 时间闸秒过
→ upcoming 恒 ~565 B；MCU 慢 → 排队深 → 堆顶后移 → min_clock 后移
→ host 少发货——**背压全程没有字节数参与，全靠时刻**。

**⑤ gen_steps → UPCOMING 的交接**——算完当场送，同一调用栈：

```c
// steppersync.c:397 steppersyncmgr_gen_steps（主线程，flush 定时器回调）
se_start_gen_steps(...)    // ① 每电机并行线程：itersolve 求根 + stepcompress 压缩
se_finalize_gen_steps(...) // ② 等全部算完
steppersync_flush(...)     // ③ 槽位闸 → serialqueue_send_batch，无间隔
```

**插补并行、发送串行**。"送过去"= 两件事：加锁挂进 `transmit_requests`
（UPCOMING 入口）+ pipe 写一个字节（`kick_bg_thread :164-167`）→ 立即返回。
消费者醒来把队列清空——**重复唤醒幂等**（pipe 字节积压无害），
这正是用 pipe 而不用信号量的原因。

进 UPCOMING 的全部前置条件：

| # | 条件 | 代码 | 不过的后果 |
| -- | -- | -- | -- |
| 1 | 轨迹已规划进 trapq | `trapq_append` | 根本不会生成 |
| 2 | itersolve 求根成功 | `se_generate_steps` | 失败 → `Internal error in stepcompress` 停机 |
| 3 | 换向合法（≥0.75 ms） | `stepcompress_append` | 整对步抹掉（有界误差 ≤1 步） |
| 4 | **MCU 槽位及时释放** | `steppersync.c:320` | **整批滞留 emitter 队列，下波重试** |
| 5 | 时间闸 ack_clock ≥ min_clock | `serialqueue.c:556` | 滞留 UPCOMING（水位上涨） |

**⑥ 三层队列 + 容量握手**（11-17 概念⑥的展开）：

| # | 队列 | 在谁的内存 | 容量谁来定 | 谁守护 |
| -- | -- | -- | -- | -- |
| 1 | host UPCOMING | host RAM | message_alloc 池 | 时间闸 `:556` |
| 2 | MCU move 队列 | **MCU RAM** | firmware 配置 | MCU 自己 |
| 3 | 影子堆 `move_clocks[]` | host RAM | = #2 容量 | 槽位闸 `:320` |

容量对齐走配置握手：MCU `get_config` 报 `move_count`（`mcu.py:1045-1047`）
→ host 扣保留槽位（homing/trsync，`:1087-1091`）→ 差值 malloc 影子堆。
**容量一致、占用靠推算**（开环模型的三条底气见 11-17⑤′）。

**⑦ 三域时间轴（一根轴串起所有钟，est_freq=20 MHz 示意）**：

```
                 host墙钟(s)   print_time(s)  MCU tick(×20e6)
① 规划期         t≈0.90        2.30           —              print_time 领先现实 0.25s
② 生成期         同次调用      2.30→2.55      flush_clock=46.0M   ← 第一次过桥
③ 影子堆/槽位闸  同次调用      —              45.99M ← min_clock  （计划域，精确）
④ UPCOMING       t≈1.10        —              45.988M ← ack_clock ← 唯一的估计
⑤ 放行+写线      t≈1.11        —              45.991M             0.1s 余量在此兑现
⑥ MCU 执行       —             2.30           45.999M 起脉冲      出生→首脉冲 ≈0.24s
⑦ 槽位释放       —             —              46.01M              堆顶前移
```

| 域 | 成员 | 性质 |
| -- | -- | -- |
| 计划域 | print_time / flush_clock / req_clock / min_clock | 精确记账 |
| 传输域 | idletime / ack_clock | **唯一估计源** |
| 执行域 | 脉冲时刻、槽位释放 | 照办 |

一个汇率（`clock_from_time`，质量 = est_freq，2-4 主题）、
一次相遇（计划 vs 传输只在 `:556`/`:645` 碰面，0.1 s 余量吸收估计误差）。
**误差在域间界面被吸收，不在域内累积。**

**⑧ 两道容量闸定稿**（闸③发送节拍已懂，重点是这两道）——
机制同源、数据集同一个，视图和阈值不同：

| | 闸① 滑窗 | 闸② RX 窗口 |
| -- | -- | -- |
| 判据 | `send_seq − receive_seq ≥ 12`（帧） | `need_ack_bytes + 64 > 192`（字节） |
| 保护的实体 | **host 自己**（丢帧时重传洪泛 ≤768B） | **MCU 硬件**（192B RX 环形缓冲溢出） |
| 阈值谁定 | 协议数学：**12 = 16 − 4**（4 位模差要求真实差 < 16，=16 会误判重复 ACK，4 帧余量吸收 OS 缓冲/线上边缘情况） | MCU 硬件上报：`serial_irq.c:17-23 DECL_CONSTANT("RECEIVE_WINDOW", 192)` → `serialhdl.py:115-118` 注入 |
| 悲观预留 | — | `+MESSAGE_MAX`：建帧前不知道长度，按最坏 64B 预留 |
| 稳态表现 | 健康链路摸不到 | 不绑定：192 = 2×64（往返管道）+ 64（余量） |
| 释放事件 | **同一个 ACK**（弹 sent_queue 时 `receive_seq++` 与 `need_ack_bytes -= len` 同时发生） | 同左 |
| 模拟器 | `-1` 哨兵显式跳过 | 字典无 RECEIVE_WINDOW → 0 → 恒不成立 |

记账闭环：`need_ack_bytes` 每建帧 `+= len`（`:529`）、每 ACK `-= len`（`:194`），
恒 = 已写线未确认字节 ≈ 最坏仍占着「OS 缓冲→线缆→MCU 缓冲」的字节数
（MCU 处理完块才回 ACK）。遗留验证项：闸②里
`last_ack_seq < receive_seq` 时 `+last_ack_bytes` 的补偿分支，
精确触发场景未锁定（与数据帧捎带确认或重传重复字节有关）。

**"一波发 12 个"三场景**：

| 场景 | 一波最多 | 真正的限制者 |
| -- | -- | -- |
| 启动/空闲后突发（真机） | 12 帧 / 768B | 闸①滑窗 |
| 真机 UART 稳态 | **~3 帧滚动**（192B 未确认即停） | 闸②先卡 + ACK 节奏（发 2-3 帧 → ACK 来一个补一个） |
| 模拟器 | 材料量多少发多少（M400 泄洪 3345B） | 只有闸③ + 时间闸 |

**⑨ 丢一包的完整剧本**（假设帧 N+1 丢失，host 在途 N+1..N+6）：

```
t1  MCU 期望序号卡在 N+1；N+2..N+6 到达 → 序号对不上 → 直接丢弃！
    （MCU 按序收块，缓冲不积垃圾）
t3  MCU 持续回 ACK，序号恒 = N+1 → host 收到重复 ACK
    （Klipper 无显式 NAK 帧——:294 注释原话 "Duplicate Ack is a Nak"）
t4  第 1 个重复 ACK：last_ack_seq 更新，不动
t5  第 2 个重复 ACK：快速重传 PR_NOW（:294-298）
t6  retransmit_event：tcflush 清 OS 写缓冲 → 从 sent_queue 队头（=N+1）
    把所有未确认帧原序、原序号拼进一个缓冲（前导 SYNC 重对齐帧界）一次写线
    → ignore_nak_seq = receive_seq（一次事故只许一次快速重传，防风暴）
    → rtt_sample_seq = 0（重发帧不采 RTT 样本，Karn 原则）
t7  MCU 这次收到 N+1 → 后续帧全部按序合法 → receive_seq 一步推进到 N+6
t8  累积确认：sent_queue 一次弹光，滑窗/字节闸全额释放 → PR_NOW 补满管道
```

恢复 ≈ 2-3 RTT，上游无感。三个让它便宜的设计：
① MCU 拒收乱序帧（缓冲不积垃圾）；② 重复 ACK 即 NAK 信号；
③ **累积确认一次追平**（host 不知道丢的是哪帧也不需要知道——
只知道 MCU 卡在 N+1，把 N+1 之后整段补上；这不是浪费：
空洞后的帧 MCU 全部拒收过，整段恰好就是 MCU 真正缺的）。

**升级路径**：若重传帧再丢——`ignore_nak_seq` 挡住第二次快速重传 →
滑窗卡 12/12 → 只能等 RTO 超时 → 走超时分支 `rto *= 2` 指数退避。
单次丢包走快速路径（快、不退避），连续丢包升级超时路径（慢、退避）。

**跨层效应**：丢包 → ACK 停 → 闸①关 → host 停发 → upcoming 水位
短暂上涨 → 30 ms 后追平回落——背压跨层传导的活例子，
全程上游规划器照常跑、无阻塞。

**设计规律**：等**计划外事件**（ACK）只能粗轮询 +0.25s 兜底 + 事件补踢
（`update_receive_seq:221` PR_NOW）；等**计划内时刻**（req_clock）
能精确睡醒——可预测性决定等待策略，与上游"控制信号全是时刻"
同一哲学。

## 自测

1. 影子堆的槽位释放时刻为什么等于批次**起点**而不是末脉冲？固件哪八行证明？
2. gen_steps 与 serialqueue 的交接是同步还是异步？"送过去"具体做哪两件事？
3. 余额会被墙钟时间影响吗？队尾 move 为什么不计入新一轮账本？

### 参考答案

1. 固件在 `stepper_load_next`（`stepper.c:66-78`）里，上一条 move 跑完
   弹出下一条的**瞬间**就 `move_free`——执行中的 move 在 `struct stepper`
   里不占槽。所以槽位释放时刻 = 某条 move **开始执行**的时刻 = 本批起点。
2. 同步移交（同一调用栈：生成线程并行算完 → `steppersync_flush` 过槽位闸
   → `send_batch` 挂队列）+ 异步消费（后台线程由 pipe 唤醒接管）。
   两件事：① 加锁挂进 `transmit_requests`；② pipe 写一个字节（幂等，
   重复唤醒无害）。
3. 不会。余额只按 move 的 `min_move_t` 累减，扣款只发生在 move 入队瞬间，
   两次入队之间墙钟隔多久都不动。队尾 move 不计入新账本是因为
   `_process_lookahead` 规划完无条件重置 0.15（`:136`）——新账本只认
   新入队的 move，尾巴的时长已属于"上一波的活"。
4. 为什么滑窗是 12 而不是 15 或 16？真机 UART 稳态下，在途帧数实际
   卡在多少、由谁决定？
5. 丢一帧后 host 从哪开始重发？为什么"整段重发"而不是只发丢的那帧
   反而不是浪费？

### 参考答案（4、5）

4. 4 位模差还原真值要求真实差 < 16（=16 的 ACK 会读成 0、被误判为
   重复 ACK），12 = 16 − 4 留余量。真机 UART 稳态在途卡在 ~3 帧：
   闸②的 192B 窗口先卡（128B 未确认恰好过，192B 停），12 帧滑窗是
   ACK 停滞时才触发的后备；真正决定发送节奏的是 ACK 驱动的 1 补 1。
5. 从 `sent_queue` 队头（= 最早的未确认帧 = N+1）按原序原序号整段重发。
   不浪费：MCU 按序收块，N+1 之后的帧到达时全被拒收——从 MCU 视角
   空洞后的每一帧都没收到，整段恰好是它真正缺的全部。配套：
   先 `tcflush` 防新旧字节交错、`ignore_nak_seq` 防重传风暴、
   重发帧不采 RTT 样本（Karn）。恢复靠累积确认一次追平（~2-3 RTT）。
